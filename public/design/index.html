New module

A module is the unit of work for all three departments at once. Declaring it here creates the folders, so mechanical, electronics and programming each have somewhere to put their first file instead of inventing a location.

Two ways in: build one from scratch, or socket in a module that already worked in a past season.

Build from scratch

Name it after the physical block, not the discipline. "Gripper Controller", not "Gripper PCB".
Only the lanes you pick get a folder. A purely mechanical module needs no hardware folder, and adding one later is fine.

Then each department starts here

Electronics — start the KiCad project in hardware/, push, then export the release before the fab order.
Programming — platformio.ini and a bring-up sketch in firmware/, on a branch.
One repo, not one per module
A new module is a folder and a commit, not a new repository. That keeps a cross-module change in a single pull request and means a junior clones one thing to see the whole robot.

Socket in a ready module

These worked. Carrying one forward copies its folder, its README, its parts.yml and its full commit history into this season, so you start from a proven board instead of a blank folder — and the lineage back to the original season stays recorded.

The loop, end to end

You cannot push to main — the branch is protected, so GitHub rejects it. Approval is not a policy anyone has to remember; it is the only path that works.

Getting your changes back

Opening a repo is one click. Tracking what you edited afterwards is the harder half — a website cannot read your hard disk, so something has to run on your side. Three routes, honest about what each one costs.

Route A · nothing to build
VS Code does the tracking

The hub's link clones and opens the repo. From there VS Code's own Source Control panel already lists every modified file and has commit and push buttons — it is the tool you were going to build. The hub polls GitHub and shows your branches back here once pushed.

AVAILABLE NOW NO LOCAL AWARENESS
Route B · recommended
One command does all five steps

A script in the repo. It branches from your change description, stages, commits, pushes and opens the pull request — the whole sequence a beginner gets wrong. No extension, no install, works on any machine that cloned the repo.

~40 LINES OF BASH STILL A TERMINAL
Route C · full automation
A club VS Code extension

The only way the hub can genuinely see your working tree. It reads git status, reports which module you are editing, and gives one "Commit & propose" button that files the pull request through the hub.

TRUE LOCAL AWARENESS SOMEONE MAINTAINS IT
Route B — the whole workflow
./scripts/propose.sh "fix encoder direction on rear-left" # branches rc26-drv-fix-encoder-direction-on-rear-left # stages everything you changed # commits with your name and that message # pushes to the club org # opens the PR and prints the review link

Start with A and B — together they cover a 30-person club, cost nothing to maintain and work on day one. Build C only if someone on the team actually wants to own an extension for two years; an unmaintained extension is worse than a terminal.

Gazebo simulation

sim/README.md

Drive the robot before it exists. The arena world is built to the season rulebook dimensions, so autonomous routines can be tuned months before the frame is welded.

cd sim colcon build --symlink-install source install/setup.bash ros2 launch rc26_sim arena.launch.py
Drive it by hand
ros2 run teleop_twist_keyboard \ teleop_twist_keyboard
Run the autonomous routine
ros2 launch rc26_sim \ auto_run.launch.py round:=1
Watch the topics
ros2 topic echo /odom rviz2 -d sim/config/rc26.rviz

Build and flash

modules/*/firmware/README.md
cd modules/drive-controller/firmware pio run # build only pio run -t upload # flash the board pio device monitor -b 115200 # serial output
The same firmware runs against the simulator with pio run -e sim, so control logic can be tested with no hardware on the bench.

Before every fab order

Export the release files and commit them. The PDF and the Gerbers are what the hub indexes and what the next batch reads — the KiCad source is for you, the release is for everyone else.

modules/*/hardware/README.md
cd modules/can-hub/hardware kicad-cli sch export pdf can-hub.kicad_sch -o release/ kicad-cli pcb export gerbers can-hub.kicad_pcb -o release/gerbers/ zip -r release/gerbers-v2.zip release/gerbers/
Fab-order checklist
Schematic PDF exported and committed
Gerbers zipped with the revision in the filename
BOM exported, part numbers not just values
Board marked as-built once it is populated and tested
Wiring diagram updated if connectors moved
Firmware pin map checked against the new revision

Your export feeds the simulation

The same STEP the archive wants is the file Gazebo needs. One script turns it into a visual mesh and a decimated collision mesh and wires it into the URDF — so the export is not paperwork, it is what lets programming test against your part.

mech/README.md
./scripts/step2mesh.sh \ modules/drive-controller/mech/RC26-DRV-MOTORMNT-v2.step # writes sim/meshes/rc26_drv_motormnt_v2.dae (visual) # sim/meshes/rc26_drv_motormnt_v2_col.stl (collision, decimated)
If you would rather not touch a terminal, dropping the STEP on this page runs the same script on the server.

Start a new season

Everything you have seen so far is a season in progress. This is the empty-page case — the twenty minutes at the start of the year that decide whether next year's batch can find anything.

Declare the robot and its modules here and the hub scaffolds the rest: the repo, the folder per module, the branch protection, the webhook, the drive folders. Nobody creates a repo by hand again.

The robot
